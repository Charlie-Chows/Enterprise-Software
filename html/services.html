FEATURED CAPABILITY

CAP-02 · POLICY ENGINE

A single source
for every decision.

The Policy Engine resolves access, change, and data decisions from a versioned document set. No hidden defaults. No inherited surprises. No configuration only one person understands.

READ THE POLICY ENGINE BRIEF
STEP 01

Declare

Every rule is written down. Rules are grouped by scope — tenant, workspace, environment, resource — so that resolution order is unambiguous and reviewable.

  • FORMAT Declarative, versioned
  • REVIEW Diff-based, like code
STEP 02

Evaluate

Resolution is deterministic. Given the same inputs, the same rule fires. Every evaluation records the rule, the subject, and the scope — exportable as evidence.

  • ORDER Deterministic, documented
  • TRACE Per-decision record
STEP 03

Stage

Changes roll out through staged channels. The same spec is applied across regions, with sign-off gates between each stage. Nothing bypasses the process.

  • CHANNELS Declared, per environment
  • ROLLBACK To any prior revision
STEP 04

Review

Every decision, every change, every rollback is written to a durable log. Auditors read the log; they do not need to ask us. The log outlives any individual engineer.

  • EXPORT Structured, queryable
  • RETENTION Configurable per tenant

CORE PLATFORM

The surfaces that stay the same.

Four surfaces, present on every deployment. Each is independently versioned and independently observable. Select to inspect a surface.

SURFACE 01 · CONSOLE

Visual control surface.

A single console for every governed action: provisioning, policy authoring, access review, deployment, and audit. The console is a view over the same model the API reads — not a separate source of truth.

  • Environment and workspace views
  • Topology and dependency map
  • Policy authoring and diff
  • Capacity and usage panels

SURFACE 02 · API

Programmatic interface.

Every console action is available over a documented API with stable versioning. Requests inherit the same policy enforcement as the console — no privileged path exists that the API cannot reach, or vice versa.

  • Versioned endpoints, breaking changes announced
  • SDKs for common runtimes
  • Deterministic response envelopes
  • Policy enforced per request

SURFACE 03 · CLI

Terminal access.

The CLI is the fastest path for engineers who live in a shell. It uses the same API, the same policy, and the same audit log. Scripted operations remain governed end to end.

  • Authenticated via the same identity fabric
  • Scriptable, idempotent operations
  • Same policy — no privileged bypass
  • Composable with existing tooling

SURFACE 04 · POLICY

Declared ruleset.

Policy is not a settings page. It is a versioned document set, authored, reviewed, and diffed like code. It resolves every decision taken by every other surface.

  • Versioned, diffable documents
  • Scope-aware resolution order
  • Per-decision trace and export
  • Staged rollout across environments

DATA & ANALYTICS

Numbers with provenance.

Every figure on the platform carries its source. Expand each panel to see what is measured, how it is measured, and where the record lives.

D-01 Operational metrics

Service-level counters, gauges, and duration histograms emitted by every platform component. Metrics are tagged with service, environment, region, and revision — so any figure can be traced back to the exact build that produced it.

  • SOURCE Platform components
  • TRANSPORT OpenTelemetry-compatible
  • RETENTION Configurable per tenant
D-02 Decision traces

Every policy resolution produces a structured trace: the subject, the resource, the scope, the rule that fired, and the timestamp. Traces are exportable as structured records — the same records an auditor would read.

  • FORMAT Structured, queryable
  • EXPORT Per-window or per-record
  • RETENTION Configurable per tenant
D-03 Data lineage

Each record that enters the platform is stamped with its source, its contract version, and the policy under which it was accepted. Lineage is written at ingestion, not reconstructed later.

  • WRITTEN At ingestion
  • SCOPE Per record
  • EXPORT Structured, filterable
D-04 Capacity envelope

Declared resource envelopes per service, per region. Observed load is compared against the declared envelope, and drift is surfaced before it becomes an incident. The envelope is part of the topology spec, not a dashboard setting.

  • DECLARED In the topology spec
  • MEASURED Against declared values
  • ALERTING On envelope breach
D-05 Change history

Every change to the platform — a policy, an environment, a contract — enters the change log. The log is immutable and searchable. Review, approval, and rollback are all visible in a single timeline.

  • MUTABILITY Append-only
  • SEARCH By actor, target, revision
  • RETENTION Configurable per tenant

Descriptions define platform surface area. Actual retention and configuration options depend on deployment.

INTEGRATIONS & APIS

How data moves through the platform.

Six processing stages, from external source to governed delivery. Each stage is independently observable and independently deployable.

STAGE 01

Source

External systems connect through a declared adapter. No source is permitted to write into the platform without a name.

STAGE 02

Edge gateway

Authentication, rate limiting, and initial schema checks happen here — before the platform accepts any record.

STAGE 03

Validation

Payloads are validated against a declared contract. Non-conforming records are rejected with a reason, not silently reconciled.

STAGE 04

Transport

Validated records move over a durable stream. Replay, backpressure, and per-topic lineage are available without additional tooling.

STAGE 05

Core

Identity, policy, and orchestration resolve every request in declared order. Each resolution produces a traceable record.

STAGE 06

Delivery

Console, API, and exports present the same governed surface. A permission enforced in one interface applies identically in the others.

DEPLOYMENT MODELS

Where the platform runs.

Three deployment models, each with a distinct operational shape and a distinct set of tradeoffs. The platform behaves identically across all three — what changes is who holds the keys.

DM-01

Cloud-managed

The platform runs in our multi-region control plane. You operate the workspaces; we operate the platform. Fastest path to a governed environment.

  • CONTROL Platform team
  • REGIONS Declared per tenant
  • DATA Tenant-isolated
DM-02

Private deployment

The platform runs inside your infrastructure. Full control over networking, storage, and identity resolution — with our operators available for review and escalation.

  • CONTROL Your team
  • REGIONS Your choice
  • DATA Your boundary
DM-03

Hybrid

The control plane runs with us; the data plane runs with you. The topology spec is shared. Regions and roles are declared on both sides and reconciled the same way.

  • CONTROL Shared, declared
  • REGIONS Split by intent
  • DATA Declared per plane

FREQUENTLY ASKED

Questions we get
in the first call.

Answers reflect how the platform is designed to behave. They are not contractual statements.

How is Stackly different from a general-purpose platform tool?

General-purpose tools model infrastructure. Stackly models the operational model — services, contracts, ownership, and the rules that govern them — and provisions infrastructure from that model. The diagram is authoritative, not descriptive.

Do we need to migrate everything at once?

No. The topology spec is designed to describe an estate in stages. Existing systems are declared as external until they are brought onto the platform. The model accommodates mixed estates from day one.

What happens if the platform is unavailable?

The control plane and data plane are separable by design. Where the deployment model allows, the data plane continues to operate under its last accepted policy set while the control plane is unavailable. Reconciliation resumes automatically when control returns.

Can we author policies without engineering involvement?

Policy documents are written in a declared syntax that reviewers from security, compliance, and engineering can read. Authoring is not restricted to engineers, but review is — every policy change passes through the same change process as code.

How do we handle a regulator's request for evidence?

The audit log and decision traces are exportable as structured records. Evidence requests are answered from the export, without involving us. If the export cannot answer a question, the question is a signal that the model has a gap.

What is not included?

Managed support during off-hours, bespoke adapter development for one-off systems, and migration of application logic. The platform governs how systems talk to each other — it does not rewrite what those systems do.
